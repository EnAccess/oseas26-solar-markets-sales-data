# Solar Market Reality — Developer Documentation

This guide describes the implementation in this repository. For the hackathon brief and project
background, see [README.md](README.md). The current backend country configuration is Rwanda (`RW`).

## 1. Project overview

Solar Market Reality is an exploratory market-analysis layer for Rwanda’s off-grid solar sector. It
helps identify places that may warrant further investigation using population, mapped electricity
infrastructure, nighttime radiance, and district-level solar-ownership survey evidence.

The checked-in processed dataset describes 1,203 analysis cells at a nominal 5 km resolution. Cells
have available indicators and an evidence level; a market-gap score is only produced when all required
need indicators and an uptake estimate are available. The score is a relative priority for field
investigation, not proof that households lack solar access or that a place is commercially viable.

## 3. Data and processing

The repository contains a committed processed dataset, so the application can start without
downloading raw data. `backend/data/raw/` is gitignored. The source-status entries in
`backend/data/processed/RW/meta.json` describe the inputs used when that processed dataset was built;
they do not mean the corresponding raw files are present in every clone.

| Dataset | Source / current role | Availability and notes |
| --- | --- | --- |
| Population raster | WorldPop 2020, 1 km; population and population density | Required raw input `data/raw/RW/population.tif`; downloaded by `scripts/ingest/fetch_population_wealth.py`. |
| Relative Wealth Index | Meta RWI via HDX; contextual indicator | Required raw input `data/raw/RW/relative_wealth.csv`; downloaded by the same script. |
| Nighttime radiance | NASA Black Marble VNP46A2 via LAADS; darkness proxy | The processed cell cache is committed at `data/processed/RW/cells_with_nightlights.csv`. Values are a single-day sample; this checkout’s metadata cannot verify the acquisition date. |
| Power infrastructure | OpenStreetMap via Overpass; mapped-grid distance, presence, and map overlay | Optional raw inputs `grid.geojson` and `power_facilities.geojson`; refreshed by `scripts/update_grid_from_overpass.py`. Coverage is incomplete. |
| Solar-device survey | Rwanda MTF household survey; district-level uptake estimate | The processed survey file is committed at `data/processed/RW/Household_Solar_Device_Use_and_Ownership.csv`. It lists solar-device-owning households and has no household GPS coordinates. |
| Administrative boundaries | GADM level-2 districts | The processed file `data/processed/RW/rwanda_districts.geojson` is committed; used for names and district survey joins. |
| Other optional inputs | GPS survey clusters, GHI raster, minigrids, GOGLA sales | Not supplied in this checkout. In particular, no GPS-labelled survey data is available to train a real-data penetration model. |

The main processing stages are:

1. **Ingest:** refresh or provide source data under `backend/data/raw/RW/`.
2. **Build:** `app.pipeline.build` combines available inputs into cell features and metadata.
3. **Serve:** the API loads the processed data into memory and builds map layers from those same cell
   values. It does not fetch source data on each request.

The primary outputs are `cells_features.csv`, `meta.json`, and `infrastructure.geojson` in
`backend/data/processed/RW/`. Missing inputs remain missing; the real-data pipeline does not replace
them with synthetic values. Synthetic data is generated only when `DEMO_MODE=true`.

## 4. Analysis grid

The grid is configured at 5 km nominal resolution by default (`GRID_RESOLUTION_KM`). The checked-in
metadata records 1,203 cells, generated by retaining cell centres inside the configured country
boundary. The grid geometry is used to generate GeoJSON map features; cell-centre coordinates and
grid indices are included in the cell data.

Current IDs run from `RW_0001` through `RW_1203`. These counts and IDs describe the checked-in build;
they can change if the boundary, resolution, or input data changes. Rebuild the processed dataset
after changing the grid resolution or relevant source data.

## 5. Potential Market Gap calculation

The single implementation is `backend/app/services/market_gap.py`. It calculates:

```text
energy_need_score = weighted mean of:
    0.4 × scale(log(1 + population density))
  + 0.4 × scale(distance to mapped grid)
  + 0.2 × (1 - scale(log(1 + nighttime radiance)))

market_gap_score = energy_need_score × (1 - solar_uptake)
```

The default weights can be changed with `NEED_W_POPULATION`, `NEED_W_GRID_DISTANCE`, and
`NEED_W_DARKNESS`. Each input is clipped to and scaled across the available country-cell 2nd–98th
percentiles. The result is from 0 to 1 internally and displayed as an integer from 0 to 100.

Uptake evidence follows this order:

1. Predictions from a model trained on real survey labels, when such a model is available and usable
   for the current dataset.
2. The MTF district estimate, calculated as survey-weighted solar-owning households divided by
   `(WorldPop district population / configured average household size)` (4.3 by default).
3. Unknown. Unknown uptake is not treated as zero, and no market-gap score is produced.

The checked-in metadata reports no labelled training cells, and no georeferenced survey clusters are
supplied. Therefore, the checked-in build has no usable real-label penetration model; where score
inputs are complete, it relies on the district survey estimate.

Evidence levels are `indicative` when a score can be calculated and district survey sample size is at
least 10 (or a trusted real-label model supplies uptake), `limited` when a score uses a district
survey estimate based on fewer than 10 sampled solar households, and `insufficient` when a required
need input or uptake estimate is unavailable. The survey estimate is shared by cells assigned to
the same district; cells whose centre is outside a district have no district survey estimate.

This is a deterministic screening heuristic, not a calibrated percentage of households without
solar and not evidence of commercial viability. Nighttime radiance is only a grid-electricity proxy:
darkness does not mean a household lacks solar. Mapped grid lines do not prove household
connections. Population can be missing or undercounted, particularly in border and lake cells.

## 6. AI assistant

The assistant endpoint is `POST /api/assistant/ask`. It uses a fixed set of six read-only tools for
location lookup, cell evidence, area summaries, comparisons, methodology, and report preparation.
Inputs and tool scope are limited; the assistant cannot execute code, SQL, shell commands, or access
files. A single request makes at most three model/tool rounds.

The implementation calls Google Gemini through its OpenAI-compatible API. Configuration is read on
the backend from `backend/.env`: `ASSISTANT_MODEL` defaults to `gemini-3.8-flash`, and the key is
read from the environment variable named `ANTHROPIC_API_KEY` (despite that variable name, the value
must be a Google AI Studio API key). Keep this key on the backend and never commit it or expose it in
frontend code. Without a configured key, the endpoint can still return retrieved project evidence,
but it does not generate an AI answer. When configured, the request sends the question, app context,
up to 10 recent history entries, and data returned by the tools to Google; tool results may contain
individual-cell as well as area-level information.

## 7. Run locally

Prerequisites: Python 3.11 or later and Node.js 18 or later.

In PowerShell, start the backend:

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements-dev.txt
Copy-Item .env.example .env
uvicorn app.main:app --reload
```

The API documentation is at <http://localhost:8000/docs>. In a second PowerShell terminal, start the
frontend:

```powershell
cd frontend
npm install
npm run dev
```

The frontend is at <http://localhost:5173>. The committed processed dataset means no downloads are
needed for a normal local run. On macOS/Linux, activate the environment with
`source .venv/bin/activate` and copy the example environment file with `cp .env.example .env`.

Backend settings are defined in `backend/app/config.py` and `backend/.env.example`. They include
demo mode, default country, grid resolution, model settings, market-gap weights and threshold, CORS,
and optional assistant and NASA Earthdata settings.

## 8. Refresh and rebuild data

Run data commands from `backend/`. A real-data rebuild requires the primary population and wealth
inputs; download them first if absent. The infrastructure script rebuilds the processed dataset
unless `--no-build` is passed. The night-lights script needs `NASA_EARTHDATA_TOKEN` in the environment
or in `backend/.env`, which the ingestion code reads.

```powershell
python scripts/ingest/fetch_population_wealth.py
python scripts/update_grid_from_overpass.py
powershell -ExecutionPolicy Bypass -File scripts/schedule/weekly_nightlights.ps1
python -m app.pipeline.build
```

The night-lights script ingests and processes its NASA cache; the final build joins the cache to the
cell dataset. Refreshing external inputs requires network access and may change the resulting
processed data.

## 9. API endpoints

The interactive API reference at <http://localhost:8000/docs> is authoritative. Country-scoped
routes accept an optional `country` query parameter; the configured default is `RW`. The cell-details
route derives the country from the cell ID.

| Method and route | Purpose |
| --- | --- |
| `GET /api/health` | Health status |
| `GET /api/countries` | Configured countries and data readiness |
| `GET /api/meta` | Dataset, grid, source, method, and model metadata |
| `GET /api/layers` | Catalog of layers available from the loaded data |
| `GET /api/map/layer/{layer_name}` | GeoJSON for one available layer |
| `GET /api/map/infrastructure` | Processed mapped infrastructure |
| `GET /api/grid/check?lat=...&lon=...` | Check the processed infrastructure snapshot near a point; this is not a live lookup |
| `GET /api/cells/{cell_id}` | Details and evidence for one cell |
| `GET /api/statistics` | Dataset summary statistics |
| `GET /api/locations/search?q=...` | Resolve a cell ID, coordinates, district, or province |
| `GET /api/locations/areas` | District and province names |
| `POST /api/reports/summary` | JSON report for selected cells (maximum 500 cells) |
| `POST /api/reports/csv` | CSV report for selected cells (maximum 500 cells) |
| `POST /api/reports/pdf` | PDF report for selected cells (maximum 500 cells) |
| `GET /api/assistant/status` | Assistant configuration status |
| `POST /api/assistant/ask` | Ask the project-data assistant |
| `GET /api/data-sources` | Source status and provenance |
| `GET /api/limitations` | Published limitations |
| `GET /api/model/performance` | Model metrics, when available |
| `GET /api/model/features` | Feature importance, when available |
| `GET /api/gogla/comparison` | GOGLA comparison; reports unavailable when the table or usable model is missing |
| `GET /api/raster/metadata` and `GET /api/raster/solar_penetration.tif` | Model raster metadata/download, only when a usable model raster exists |

Layer IDs include `market_gap`, `population`, `night_lights`, `grid`, `survey_solar`,
`relative_wealth`, `population_total`, and `solar_penetration`. The API layer catalog filters out
layers whose data column is missing or entirely empty. `population_total` and `solar_penetration`
are not standard UI selectors; predicted solar penetration is only available when usable model
outputs exist.

## 11. Data provenance and development practices

Source metadata is defined in `backend/app/data_sources.py` and combined with build metadata for
`GET /api/data-sources`. When adding or changing a dataset:

1. Record its source, licence, retrieval date, and other available provenance.
2. Update the ingestion/processing pipeline and generated metadata.
3. Check the frontend data-source display and API documentation.
4. Preserve missing values and describe coverage limitations accurately.
5. Keep raw inputs separate from generated outputs.

API routes should validate requests and delegate calculations to services. Keep configuration in
environment settings and protect secrets.

## 12. Troubleshooting

- **Missing `meta.json` or processed cells:** rebuild the dataset; for real mode, first provide the
  required population and relative-wealth raw files.
- **Missing Python packages:** install `backend/requirements-dev.txt` in the active virtual
  environment.
- **Frontend install/build problems on Windows:** the frontend pins a WebAssembly Rollup override
  in `frontend/package.json`; install dependencies from that directory and retry `npm run build`.
- **Rasterio/GDAL import errors:** use compatible Python and geospatial package versions from the
  backend requirements in the selected environment.
- **Assistant does not generate answers:** verify that `ANTHROPIC_API_KEY` contains a Google AI
  Studio key, `ASSISTANT_MODEL` names an available Gemini model, and the backend has been restarted.
- **Missing indicators or layers:** check whether the source input is present, whether the processed
  cell column has values, and the source status in `/api/data-sources`.
